ColorsN

컬러 시스템은 시각적 일관성을 유지하고 효율적인 디자인 작업을 돕습니다. Neutral(중립 회색)이 화면의 바탕이고, Primary(제품 메인 컬러)는 핵심 정보를 강조하는 데만 씁니다. 상황에 맞는 색을 이름으로 고를 수 있도록 Semantic 토큰으로 제공하며, 스와치를 클릭하면 Hex · RGBA · 토큰 값을 볼 수 있고, 토큰을 복사할 수 있습니다. 어느 색을 어디에 쓰는지는 Brand role map 에 있습니다.

역할 문법 — --{intent}-{role}[-{state}]

토큰 이름이 공개 API 입니다. 제공 형태가 React 패키지와 HTML+CSS 둘이라, 개발자가 이 페이지에서 본 단어를 그대로 타이핑합니다. 그래서 이름이 역할을 드러냅니다 — 어떤 색인지가 아니라 어디에 쓰는 색인지가 이름에 있습니다.

종전에는 토큰 하나가 역할 셋을 겸했습니다. 그 결과 심각도 토큰이 면·글자·면 위 글자를 겸해 10 조합 중 8이 AA 미달이었고, 제품 Primary 가 면·텍스트·지표를 겸해 패널 위에서 4.08 이었습니다. 역할을 가르는 것이 이 체계의 출발점입니다.

역할뜻대비 기준알파
surface채운 면 — 버튼·채운 태그·배너면 자체는 기준 없음(라벨이 식별을 맡습니다)솔리드
fill옅은 면 — 태그 바탕·선택 행·알림 배경—알파
on면 위 글자·아이콘4.5 — 자기 surface 세 상태 전부솔리드
text옅은 바탕 위 글자·아이콘4.5 — 세 표면과 자기 fill 전부솔리드
line보더 · 구분선컴포넌트 경계 3 · 장식 구분선 면제알파
graphic글자 없는 지표 — 바·점·밴드·링3 — 세 표면 전부솔리드

상태는 surface 에만 붙습니다(-hover · -pressed). 포커스는 전역 하나(--focus-ring)입니다.

알파는 fill 과 line 에만 씁니다. text·on·surface·graphic 에 알파가 들어가면 같은 토큰이 바탕마다 다르게 측정돼, 어떤 바탕에서는 AA 를 넘기고 다른 바탕에서는 못 넘깁니다 — 종전에 --text-tertiary 가 캔버스 4.74 · 패널 3.97 이었습니다.

어떻게 고르나

역할을 먼저 정하고(면인가 글자인가 지표인가) 의도를 고릅니다. 반대 순서로 하면 "제품 파랑"을 글자에 그대로 써서 대비가 깨집니다 — 종전에 가장 자주 난 실수입니다.

/* 역할을 먼저 정하고(면인가 글자인가 지표인가) 의도를 고른다 */

/* 면 + 그 위 글자 — 둘은 항상 짝이다 */
.btn.primary{
  background: var(--accent-surface);
  color:      var(--accent-on);
}
.btn.primary:hover { background: var(--accent-surface-hover); }
.btn.primary:active{ background: var(--accent-surface-pressed); }

/* 옅은 바탕 + 그 위 글자 — 면 토큰을 글자에 쓰지 않는다 */
.tag.accent{
  background: var(--accent-fill);   /* 알파 — 어떤 표면 위에서도 같은 깊이 */
  color:      var(--accent-text);   /* 세 표면과 자기 fill 전부에서 4.5 */
}

/* 글자가 올라가지 않는 지표 — 3:1 만 넘기면 된다 */
.progress.danger i{ background: var(--danger-graphic); }

/* 보더 */
.notice.danger{ border-color: var(--danger-line); }

/* 하지 말 것 */
.kpi .value{ color: var(--danger-surface); }  /* 면 토큰을 글자에 — 라이트 4.58 */
.dot{ background: var(--red-500); }           /* 프리미티브 직접 참조 — 빌드가 막는다 */
// 같은 토큰을 같은 규칙으로 씁니다. 클래스 마크업이 같아 스타일시트 하나로 동작합니다.
import "@jiran/ds-react/style.css";
import { Button, Tag } from "@jiran/ds-react";

<Button variant="primary">정책 저장</Button>   {/* --accent-surface + --accent-on */}
<Tag tone="accent">Accent</Tag>                {/* --accent-fill    + --accent-text */}
<Tag tone="critical">Critical</Tag>            {/* 심각도 → danger-strong 매핑 */}

층은 셋이고 참조 방향이 한쪽입니다 — Primitive(램프) ← Semantic(이 페이지) ← Component. 컴포넌트가 램프를 직접 참조하면 빌드가 실패합니다. 새 색이 필요하면 램프에서 골라 의미 토큰을 하나 늘립니다.

Theme — 의도 없는 색

테마 자체를 이루는 색입니다. 의도 접두어가 없습니다 — 제품이 바뀌어도, 상태가 무엇이어도 같습니다. 전부 중립 램프를 참조합니다.

Surface

표면 네 단계입니다. base 는 페이지, raised 는 카드·팝오버·모달, sunken 은 들어간 영역(예제 캔버스·패널), inverse 는 툴팁·토스트입니다. 넷 다 솔리드입니다 — 표면이 반투명하면 그 위의 글자 대비를 한 값으로 보장할 수 없습니다.

Text

글자와 아이콘입니다. 흰 바탕에서 primary 17.4 → secondary 9.0 → tertiary 6.7 로 단계가 벌어집니다. tertiary 를 중립 500 으로 내리면 sunken 위에서 4.43 으로 떨어져 600 에 둡니다. disabled 는 1.4.3 면제 대상이라 2.33 입니다.

Fill

옅은 면입니다. 중립 500 을 베이스로 한 알파여서 어떤 표면 위에서도 같은 깊이로 얹힙니다 — 그래서 선택 행·트레이·태그 바탕에 씁니다. disabled 도 알파입니다: 솔리드 단계로 두면 다크에서 --surface-sunken 과 같은 값이 돼 비활성 컨트롤이 패널에 묻힙니다(구분 1.00).

Muted

중립을 하나의 의도로 세운 것입니다. 심각도 Info 등급과 비활성 지표가 씁니다. surface·on·graphic 셋만 둡니다 — fill 과 text 는 위 --fill-strong·--text-tertiary 와 값이 같아 따로 선언하면 중복입니다. graphic 은 글자 없는 점·범례 칩이라 3:1 이 필요합니다(종전 중립 400 은 흰 바탕 2.73 으로 미달이었습니다).

Focus · Static

포커스 링은 제품 색을 쓰지만 전역 하나입니다 — 컴포넌트마다 다른 링은 키보드 사용자에게 혼선입니다. 캔버스와 3:1 을 넘겨야 하고, 밝은 제품에서는 한 단계 짙게 내려갑니다. Static 은 테마에 상관없이 고정된 색이라 반전 표면 위 글자처럼 테마가 바뀌어도 같아야 하는 자리에만 씁니다.

Material

팝업처럼 층위가 생길 때 뒤를 어둡게 덮는 색입니다. 알파라 뒤가 비칩니다 — 체커 바탕으로 표시했습니다.

Intent — 의도 × 역할

의도 여섯과 역할 여덟의 조합입니다. 열이 역할이라 같은 역할이 의도를 가로질러 같은 자리에 섭니다 — "면이 필요하면 -surface, 글자면 -text" 가 의도와 무관하게 같은 규칙입니다. 칸을 누르면 Hex·RGBA·토큰 값이 나옵니다.

열 머리의 숫자는 그 역할이 넘겨야 하는 대비입니다. fill 과 line 은 알파라 체커 바탕으로 표시했습니다.

제품 메인 컬러는 값이 아니라 슬롯입니다. HEX 하나를 주면 accentScale() 이 --accent-50~900 열 단계를 만들고, applyAccent() 가 그것을 주입합니다. 나머지 토큰은 전부 공통이라 제품마다 다시 정의할 것이 없습니다. 헤더의 Accent 선택으로 이 페이지 전체를 미리볼 수 있습니다.

슬롯이라 두 가지 예외 경로가 필요합니다 — 제품 색이 상태색과 겹칠 때, 그리고 제품 색이 밝아서 흰 글자가 뜰 때입니다. 둘 다 applyAccent 가 판정해 루트 속성으로 켭니다.

상태색과 겹칠 때 — 중립 전환

제품 메인 컬러가 상태색(Negative · Cautionary · Positive · Informative)과 색상환에서 15도 미만으로 가까우면, 채워진 Primary 버튼이 "삭제" 나 "완료" 로 읽힙니다. 한 화면에서 같은 색이 브랜드와 상태 두 가지 뜻으로 읽히는 상태라, 이때는 제품 컬러가 쓰이는 곳을 전부 중립으로 내립니다 — 버튼만이 아니라 링크 · 탭 활성 · 체크박스 · 선택 행 · 포커스 링, 아래 Atomic 의 Accent 램프까지 함께입니다.

방법은 토큰을 따로 두는 것이 아니라 램프를 갈아끼우는 것입니다. 주입하는 램프(--prod-50~900)에 제품 HEX 로 만든 스케일 대신 무채색 10단계를 넣으면, 이 램프를 참조하는 --accent-surface · --accent-surface-hover · --accent-surface-pressed · --accent-fill · --accent-on · --accent-text-inverse · --focus-ring 가 한꺼번에 따라옵니다. 단계 값은 두 테마 모두 --neutral-* 와 같습니다 — 종전에는 라이트만 slate 를 써서 주변 중립(#989BA2)과 #94A3B8 로 한 톤 어긋났습니다.

다만 라이트에서 메인은 gray/900 이어야 하므로, 네 토큰의 단계를 조정합니다 — 진한 바탕은 눌렀을 때 밝아지는 쪽이 자연스럽고, 회색 50 은 흰 캔버스에서 선택 행 배경으로 보이지 않습니다. 다크는 거울입니다 — 어두운 바탕에서는 밝은 쪽이 주인공이어야 해서 메인이 100 이고, 눌릴수록 짙어집니다. 중립 600(#5A5C63)은 다크 캔버스 위에서 대비가 2.0 밖에 안 돼 주인공이 될 수 없습니다. 램프를 갈아끼우는 것 자체는 두 테마에 함께 걸리고, 단계 조정만 테마별로 갈립니다.

밝은 메인 컬러 — 글자색과 상태 방향

중립 전환과 같은 성격의 자동 보정이 하나 더 있습니다. 메인 컬러가 밝으면 그 위의 흰 글자가 뜹니다 — 아래 제품 A(#00AAB6)는 흰 글자와 2.83:1 로 AA 미달이고, 어두운 글자와는 6.33:1 입니다. 그래서 applyAccent 가 양쪽을 재어 대비가 높은 쪽을 고르고, 밝은 제품이면 <html data-accent-light> 를 켭니다. 상태색과 겹치는 제품은 무채색 램프라 늘 흰 글자여서 이 플래그와 함께 켜지지 않습니다.

글자색만 바꾸면 끝이 아닙니다. hover · pressed 가 글자 반대쪽으로 가야 합니다. 흰 글자 제품은 짙어지는 쪽(700 · 800)으로 가면서 글자 대비가 5.2 → 7.6 → 10.8 로 좋아집니다. 그런데 어두운 글자 제품을 같은 방향으로 보내면 6.3 → 4.1 → 2.6 으로 깨집니다. 그래서 밝은 제품은 밝아지는 쪽으로 갑니다 — 라이트는 기준 600 에서 500 · 400, 다크는 기준 500 에서 400 · 300 입니다(6.3 → 8.1 → 10.9). 방향은 두 테마가 같고 출발점만 한 단계 다릅니다.

다크에서 제품 컬러와 중립의 경계

다크는 두 줄로 나뉩니다. 화면의 바탕 — 배경 · 패널 · 서피스 · 텍스트 · 보더 · 라인 · Fill — 은 제품과 무관하게 아래 Atomic 의 Neutral 램프를 씁니다. 제품이 바뀌어도 다크 화면의 톤은 같습니다. 반대로 Primary 신호 — 주요 버튼 · 체크박스 · 라디오 · 스위치 · 탭 활성 · 링크 · 포커스 링 · 강조 배너 — 는 제품 메인 컬러를 씁니다.

그리고 다크는 기준 단계만 한 단계 다릅니다 — 라이트 600 · 다크 500(위 기준 단계). 글자색(--accent-on)과 밝은 제품 판정은 두 테마가 공유하고, hover · pressed 는 기준에서 글자색 반대 방향으로 갑니다. 그 밖에 다크에서 다른 것은 아래 다섯뿐입니다.

선택 배경만 제품과 무관하게 중립입니다. 선택된 표 행 · 메뉴 · 사이드내비 · 카드의 배경이라 배경 계열로 묶어 --neutral-700 에 둡니다 — 제품 램프의 900 을 쓰면 다크 캔버스와 1.05~1.16 이라 선택된 행이 사라집니다. 선택 표시는 그 위의 글자와 보더가 제품 컬러로 담당합니다.

제품에서는 램프를 --prod-* 로 주입하고, 상태색과 겹치면 <html data-accent-neutral>, 메인 컬러가 밝으면 <html data-accent-light> 를 함께 켭니다 — 주입 함수는 Design Token › Accent 스케일 생성 에 있고, 상태색과 겹치는지 판단하는 부분까지 들어 있습니다. 중립으로 가도 아래 제품 카드의 스와치와 헤더의 색상 선택 점은 제품 컬러를 유지합니다 — 그 색의 HEX 를 함께 적어 두는 자리라, 회색으로 칠하면 칩과 적힌 값이 어긋납니다. 카드에서 골라 보면 사이트 전체가 바로 바뀝니다.

Status & Severity — 두 축, 같은 색

상태(Positive · Cautionary · Negative · Informative)와 위협 심각도(Critical ~ Info)는 다른 축이지만 같은 토큰을 씁니다. 그 선택의 비용과 그래서 생긴 제약이 아래에 있습니다.

기준 단계 — 라이트 600 · 다크 500

제품 Primary 와 네 상태색은 같은 기준 단계를 씁니다 — 라이트는 600, 다크는 한 단계 밝은 500 입니다. 다섯 가족이 같은 단계에 서 있어야 한 화면에서 상태색이 제품색보다 떠 보이지 않습니다.

나머지 토큰은 기준에서 기계적으로 나옵니다. 핵심은 hover · pressed 가 면 위 글자색의 반대 방향으로 간다는 것입니다 — 흰 글자면 짙은 쪽, 어두운 글자면 밝은 쪽. 반대로 보내면 글자가 깨집니다(어두운 글자를 짙은 쪽으로 보내면 6.3 → 4.1 → 2.6). 다크에서는 네 상태색이 모두 어두운 글자를 쓰므로 상태가 밝은 쪽으로 갑니다.

심각도 — 독립 축이 아니라 상태색 + 등급

보안 도메인의 위협 심각도 5단계는 Status 와 다른 축이지만, 색은 따로 두지 않습니다. 종전에는 --sev-* 20개가 독립 축이었는데 한 토큰이 면·글자·면 위 글자를 겸해 10 조합 중 8이 AA 미달이었고, 그 20개의 대비 수치는 빌드가 검증하지 않아 계속 낡았습니다. 지금은 등급을 상태색 의도로 매핑하고, 매핑된 토큰은 다른 의미 토큰과 똑같이 게이트가 잽니다.

이 선택의 비용 둘. 하나 — 상태색과 심각도가 같은 토큰을 쓰므로 두 축이 한 화면에서 구분되지 않습니다("처리 실패"와 "High"가 같은 빨강). 그래서 Brand role map 의 "한 요소에 두 축을 겹치지 않는다 · 심각도는 항상 라벨 병기"가 권고가 아니라 제약입니다. 둘 — Critical 과 High 가 같은 빨강이라 옅은 태그에서는 바탕의 짙기가 유일한 단서입니다. 같은 알파로 두면 분리가 라이트 1.04 · 다크 1.09 로 지각 가능 바닥(1.1)에도 못 미쳐, danger-strong 은 fill 알파도 강한 쪽(라이트 16% · 다크 20%)으로 잡았습니다 — 라이트 1.23 으로 갈립니다.

다섯 등급이 구분되는지는 빌드가 검사합니다. 대비 비율은 휘도만 보므로 색조 차이를 잡지 못합니다 — Medium(주황 #FF9200)과 Low(청록 #00BDDE)는 휘도가 1.00 으로 같습니다. 그래서 색조 계열표(red · orange · cyan · neutral)를 contrast.pairs.js 에 선언하고, 같은 계열이면 ΔL* ≥ 8, 계열이 다르면 값 상이를 요구합니다. Critical↔High 는 라이트 ΔL* 26.7 · 다크 18.0 입니다. 다만 이 다섯 색은 회색조로는 분리할 수 없습니다 — 상태색 램프를 공유하는 한 만들 수도 없습니다. 색만으로 의미를 전달하지 않는다(1.4.1)는 전적으로 라벨 병기에 의존하고, 그 라벨이 있는지는 verify.js 가 검사합니다(도넛·밴드의 접근 이름, .sev-cell 의 같은 칸 글자).

대비 게이트는 "글자가 바탕에서 읽히는가"만 봅니다. 그것과 "단계들이 서로 고르게 벌어졌는가"는 다른 질문입니다 — 세 단계가 모두 AA 를 넘기면서도 둘이 거의 같은 톤일 수 있습니다. 아래는 빌드가 잰 CIE L* 입니다(대비 비율은 중간 밝기끼리의 거리를 과소평가해서 '낙폭'의 축으로는 맞지 않습니다).

균형은 단계들이 한 화면에 함께 보이는 사다리에만 요구합니다. 본문·보조·설명은 같은 단락에 나란히 서지만, rest → hover → pressed 는 셋이 동시에 보이는 일이 없습니다. 상태 사다리에는 "변화가 느껴지는가"(최소 낙폭)만 묻습니다.

지금 동시에 보이는 사다리 넷이 모두 기준을 못 넘깁니다 — text 는 두 모드 모두 첫 낙폭이 둘째의 2.5배라 Secondary 와 Tertiary 가 거의 같은 톤이고, line 은 3.3~3.8배입니다. 라이트 surface 는 base 와 raised 가 둘 다 흰색이라 명도 분리가 0 이고 경계를 보더·그림자가 전담합니다. 교정은 보고 결정하기로 했으므로 빌드를 막지 않고 매 빌드 보고합니다 — 방향이 뒤집힌 경우만 실패입니다.
